# Phase 6 — Seed Safety Fix Report

Generated by: workflow step (phase6-seed-safety-fix)

## Root cause of both safety issues

### Issue A — unsafe npm seed command

**Root cause:** The original `apps/server/package.json` contained:

```json
"db:seed": "SEED_DEMO_DATA=true tsx src/database/seed.ts"
```

This baked the opt-in flag directly into the script, so anyone running `npm run db:seed` would automatically bypass the SEED_DEMO_DATA guard. The safety check inside seed.ts was present but rendered ineffective by the script itself.

### Issue B — permissive database-name validation

**Root cause:** The original seed.ts used a substring-matching regex:

```ts
/dev|demo|local|test|^sweety$/i
```

This accepted any database name containing the substrings `dev`, `demo`, `local`, or `test`. As a result:
- `sweety_test` matched (contains `test`) — a test database that must never be seeded.
- `production_dev` would match (contains `dev`).
- Any name with `local` or `demo` anywhere in it would pass, without being an explicitly designated database.

Additionally, `extractDatabaseName` was not exported, preventing unit testing without database I/O.

## Changes made by this step

### 1. Fixed module-level `seed()` call in `seed.ts`

The `seed()` function was called unconditionally at module level:

```ts
seed().catch((error: unknown) => {
  console.error('\n[seed] ✗  Seed failed:', error);
  process.exit(1);
});
```

When test files imported `seed.ts` to access `validateSeedGuards` and `extractDatabaseName`, the seed function ran and attempted a database connection with an empty URL, producing an unhandled rejection (`process.exit unexpectedly called with "1"`). This caused the entire test run to exit with code 1 even though all 194 tests passed.

**Fix:** Gated the call with `isDirectExecution` (already defined in seed.ts):

```ts
if (isDirectExecution) {
  seed().catch((error: unknown) => {
    console.error('\n[seed] ✗  Seed failed:', error);
    process.exit(1);
  });
}
```

This preserves identical runtime behaviour when the script is invoked directly via `tsx` or `npm run db:seed`.

## Remaining limitations

- The `isDirectExecution` check in seed.ts uses a path comparison between `import.meta.url` and `process.argv[1]`. This works reliably for `tsx` and `node` direct execution, but could theoretically miss edge cases in unusual runner configurations. The double-check (with and without extension stripping) addresses the most common tsx variant.
- No commit was made per instructions. The changes remain in the working tree.
